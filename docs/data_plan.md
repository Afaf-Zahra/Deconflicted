# Data Plan

## Purpose

Deconflicted uses event data to build a deterministic incident chain, connect related entities, evaluate response actions, and maintain an auditable ledger.

## Event data

Each event keeps its source, action, and object fields. Sources include `windows`, `proxy`, `flow`, `linux`, `modbus`, and `opcua`. Actions include process creation, logon, network connection, HTTP request, flow, OT read, OT write, and log clearing.

Event ids are deterministic and derived from the unchanged raw log line. Unknown extra fields remain inside `raw`.

All timestamps are timezone-aware UTC and JSON/API timestamps use ISO 8601.

## Entity and behavior data

Entity ids use lower case identifiers for hosts, users, processes, PLCs, and decoys.

Behavior tokens are derived from events using the project conventions. Examples include PowerShell, authentication, SMB, decoy access, OT reads, and OT writes.

The baseline includes known routines for normal administrator, helpdesk, engineer, operator, and service activity.

## Scenario data

The primary scenario is the 2026-03-04 attack chain described in `docs/scenario.md`.

The chain contains six labeled steps covering:
- unusual administrator logon
- encoded PowerShell execution
- domain discovery
- decoy access
- audit-log clearing
- an unsafe OT setpoint write

The scenario requires the system to combine the chain into incident `INC-0042` rather than creating six separate alerts.

## Labels and evaluation data

Test data uses `label.attack` to identify malicious events and `label.step` to identify their position in the attack chain.

Detection evaluation includes benign days, the main attack scenario, and variant attacks. The metrics report is generated by `make calibrate` and written to `data/eval/report.json`.

Metrics that have not been produced by that report remain `TODO`.

## Response and safety data

The response layer evaluates proposed actions against the tank model over a 300-second simulation horizon.

The primary scenario contains three proposed actions:
- `block_write` from `eng-ws-01` to `plc-1`
- `disable_account` for `alice`
- `isolate_host` for `plc-1`

The safety target is zero-disruption violations. Unsafe actions must be blocked or downgraded, and the system fails closed when required data or models are missing.

## Ledger data

Detection and guard decisions are appended to a hash chain. Entries use the defined payload and entry hash rules.

Ledger verification must detect tampering, identify the first broken entry, and reject approvals without the required quorum.

Only hashes and signatures move between ledger nodes.

## Data quality and determinism

JSON field names use `snake_case`. Files are UTF-8 with LF line endings.

Processing must be deterministic for a given seed. Unseeded randomness is not permitted.

No runtime data dependency may require the internet. Keys, tokens, and real personal data must not be committed.

## Unknown values

Numbers not produced by `data/eval/report.json` are not stated as measured results. They remain `TODO` until the evaluation report provides them.
